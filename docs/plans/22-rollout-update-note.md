# 22. 순차 배포와 응답의 업데이트 알림 (5.1.2)

> 사용자가 10-16에 5.1.2 범위로 정했다("ㅇㅇ 5.1.2에 넣는걸로 하자 …"). 서버 쪽 구현은 스위치를 끈 채 main에 있다. 서버 설치와 켜기는 사용자 OK 뒤에 한다. 앱 쪽(알림을 보고 바로 확인하기)은 Mac이 한다.

## 1. 업데이트 알림 (`pokeserver update-note on|off`)

- 서버에 이 앱이 받을 더 새 버전이 있으면, 트레이너가 보내는 모든 POST 응답(로그인 · act · 팀 · 로비 · 우편 · 원정 · 장터 · 대전 …) 맨 앞에 이것이 붙는다:

```json
{"update":{"urgent":true,"v":"5.1.2"}, …원래 응답…}
```

- 조건:
  - `v`는 /v1/update가 이 앱에 줄 버전이다(아래 §2의 순차 배포를 따른다).
  - 앱의 버전은 User-Agent(`PokeWalker/<버전> (<mac|windows>)`)로 본다. `v`가 그보다 새로울 때만 붙고, 아니면 응답은 지금과 바이트까지 같다.
  - `urgent`는 /v1/update의 urgent(update-hint)와 같다.
  - 3.9 이하 Windows(고장 난 zip 업데이터)에는 붙지 않는다.
- 붙이는 방법: 서버가 응답 텍스트의 맨 앞 `{` 뒤에 끼워 넣는다. 나머지는 그대로라 옛 앱은 모르는 키로 건너뛴다. 테스트로 옛 ActReply 모양이 읽히는 것을 확인했다.
- 공유 모델: `UpdateNote {v, urgent}`(Sources/Model/Engine.swift), `ActReply.update`(옵션)
- **앱이 할 일(5.1.2, Mac):**
  - 2xx 응답 본문이 `{"update":`로 시작하면 그 값을 읽는다. 맨 앞이라 앞부분만 보면 된다.
  - `v`가 자기 버전보다 새로우면 /v1/update를 바로 확인한다(매시 확인을 기다리지 않음).
  - 같은 `v`로는 10분에 한 번까지만 확인한다.
  - 그 뒤 설치는 지금 업데이터 그대로다(urgent면 바로).

## 2. 순차 배포 (`pokeserver rollout off | <n>% | <id>[,<id>…]`)

- 후보 릴리스는 두 번째 폴더 `release-next`(`NEXT_RELEASE_DIR`, 없으면 `RELEASE_DIR`-next)에 둔다.
  - 넣기: `RELEASE_DIR=/var/lib/pokewalker/release-next server/publish.sh v<버전>`(같은 서명 · 크기 · SHA-256 검사)
  - `release`는 그대로 모두의 것이자 페이지의 것이다.
- **누구:** 트레이너 키로 정한다(추천).
  - 한 사람의 여러 PC가 같은 버전을 받고, 5.0부터의 /v1/update가 트레이너를 보낸다.
  - 기기 ID는 /v1/update에 오지 않고, PC를 바꾸면 갈린다.
  - `<id>,…`: 이름으로 고른다(먼저 써 볼 몇 명).
  - `<n>%`: 키와 후보 버전의 해시로 0~99를 정해서 n 미만이 받는다. 넓히면(20 → 50 %) 먼저 받은 사람은 그대로 들어 있다. 다음 버전에서는 다른 사람이 먼저 받는다.
- **안정 버전에 이미 있는 앱만 후보를 받는다.** 더 오래된 앱은 먼저 안정 버전을 받고, 다음 확인에서 후보를 받는다. 그래서 다운로드(GET, 트레이너 없음)를 User-Agent 버전만으로 가를 수 있다.
  - 안정 버전 이상이고 후보보다 낮은 앱은 후보의 파일을 받는다(후보를 받은 앱만 내려받는다).
  - 그 밖의 앱은 안정 버전의 파일을 받는다.
  - 옛 앱(5.1.1)도 바꿀 것이 없다.
- 후보에 그 플랫폼의 업데이트 파일(mac zip, Windows setup.exe)이 없으면 안정 버전을 준다.
- **멈추기:** `pokeserver rollout off`. /v1/update가 모두에게 안정 버전을 준다.
  - 이미 후보를 받은 앱은 그대로 쓴다. 앱은 버전을 내리지 않는다.
  - 되돌리려면 더 높은 버전을 내거나, 그 사람이 페이지의 안정 버전을 손으로 설치한다.
- **마무리:** `server/publish.sh v<버전>`(안정 자리 · 페이지)을 한 뒤 `pokeserver rollout off`. 후보가 안정 버전과 같아지면 순차 배포는 저절로 아무 일도 하지 않는다.
- **상태:** `pokeserver rollout`. 두 버전, 계획, 알림 스위치, 이번 주에 본 트레이너 중 후보 대상과 그 앱 버전을 보여 준다(테스트 ID 제외).
- 실행 중인 서버는 두 폴더의 서명된 manifest와 설정을 10초마다 다시 읽는다(content 스위치와 같이).

## 3. 확인

- 서버 테스트 150/150. RolloutTests:
  - 대상 · 두 단계 · 플랫폼 · 끔 · 승격
  - 몫 20 %가 약 400/2000이고, 넓혀도 먼저 받은 사람이 그대로 남음
  - 다운로드 갈림, 알림 JSON과 끼워 넣기, 옛 ActReply 읽기, 설정 · 잘못된 이름 거절
- 실제 서명된 릴리스로 끝까지(임시 서버 · 임시 DB · 다른 포트, 라이브 무관; 안정 = 5.1 사본, 후보 = 5.1.1 사본, 대상 1명):
  - /v1/update:
    - 대상 5.1 mac · windows → 5.1.1
    - 대상 아닌 5.1 → 5.1
    - 대상 5.0.1 → 5.1
    - 3.9 Windows → null
    - 받은 manifest가 공개 키로 서명 확인됨
  - 다운로드:
    - UA 5.1 → 5.1.1의 mac zip · setup.exe 크기
    - UA 5.0.1 · 5.1.1 → 5.1의 파일
  - 알림:
    - 대상 5.1의 로그인 · 팀 응답 맨 앞에 `{"update":{"urgent":false,"v":"5.1.1"}`
    - 대상 아닌 5.1에는 없음
    - 5.0.1에는 `v` 5.1
  - 둘 다 끄면 지금과 같음
